## 4. 分析（數據支持）

### 4.1 首字 vs 完整

| 指標 | 約略 |
|------|------|
| 串流 first_token 中央値 | **~2.5 s** |
| 串流 complete 中央値 | **~6.3 s** |
| 首字之後到完成 | **~3.5–4 s** |

→ **既不是「只卡在開頭」也不是「開頭瞬間出字但拖很久」的單一型**；  
**等待開始約 2.5s，生成續寫約 3.5–4s，兩者都明顯。**

### 4.2 純聊 vs 記憶召回

| | 中央／平均 total |
|--|------------------|
| 純文字非串流 | ~6.1 s |
| 記憶召回非串流 | ~5.7 s |

在本次樣本下，**記憶召回並未比純聊更慢**（甚至略快，可能題目更短／LLM 波動）。  
**不能**把「慢」主要歸咎於記憶召回本身。

### 4.3 前三大耗時來源（在**可觀測 client 數據**下的排序）

| 順位 | 來源 | 證據 |
|------|------|------|
| **1** | **LLM 等待首字（TTFT + 前置管線）** | first_token 中央 ~2.5s，純聊亦然 |
| **2** | **LLM 串流生成（首字後）** | complete − first ≈ 3.5–4s |
| **3** | **其餘（網路 RTT + 記憶／Supabase／Redis 合計）** | 無 server stage 拆帳；但 B≈D 顯示記憶不是主增項 |

**明確：** 本次 **無法**從 log 拆出 `llm_stream_ms` / `embedding_ms` / `redis_ms` 的伺服器真值；上表是 **client 可證** 的階段歸因。

### 4.4 Redis 是否改善速度？

| 問題 | 結論 |
|------|------|
| Redis 是否 real 工作？ | **是** |
| 是否比「無 Redis／Mock 時期」更快？ | **無法嚴格判定** — 缺少同條件舊版逐筆對照 |
| Redis 是否像主瓶頸？ | **不像** — ping_ms≈0；記憶召回未拉長 total |
